# MarinOS security system — foundational decisions

This document records the decisions Phase 1 of the security implementation plan asked for, before any schema or tooling work starts. See the plan itself for full context; this file is the durable record.

## Scope

`security.json` applies to **deployed apps only** — not `marin-ui`, `marin-skills`, or `marin-digital-standards`, which aren't deployed applications.

The confirmed deployed-app list, cross-checked against `marin-os/catalog.json` and each repo's own `marin.yml`:

| Repo | In `catalog.json`? | `marin.yml` type | Deployment target |
|---|---|---|---|
| `marin-magic` | yes | app | github-pages |
| `marin-docs` | yes | docs | github-pages |
| `marin-mentions` | yes | app | github-pages |
| `marin-anonymizer` | yes | app | github-pages |
| `marin-zipper` | yes | app | github-pages |
| `marin-unzipper` | yes | app | github-pages |
| `marin-os` | n/a (doesn't list itself) | platform | github-pages |

`marin-os` is in scope even though it doesn't appear in its own catalog — it's the platform's own deployed site (Phase 4).

**Not in scope:**
- `marin-ui` — library, `deployment.target: none`.
- `marin-skills`, `marin-digital-standards` — no `marin.yml`; not deployed applications.
- `marin-app-template` — has `deployment.target: github-pages` in its own `marin.yml`, but it's a scaffold, not a production app end users use. It gets a **starter** `security.json` (Phase 17) so new apps built from it are secure by default, but it is not tracked in the security inventory (Phase 13) as an app in its own right.

## Catalog

`marin-os/catalog.json` is **not** extended with security fields. It stays scoped to what it already does — runtime nav/catalog display. The security inventory (Phase 13) is generated by cross-referencing `catalog.json`'s app list against each app's own `security.json`, which remains the sole source of truth for security data. This avoids hand-syncing security review data into a file that every app's nav dropdown fetches live at runtime.

## Routing

Every MarinOS app is a single-page static site using hash-based tab sections (`data-tab-section`, e.g. `#about`, `#updates`) — there is no path-based routing. Security is exposed as `#security`, not a `/security` page. `.well-known/security.txt` is the one genuine exception — it's a real static file at a real path, not a route.

No Accessibility/Privacy link bundling in this phase. Neither exists anywhere in the codebase today; Security lands alone in `#about` for now (`Security → #security`). Establishing a broader About/Accessibility/Privacy/Security convention is a separate decision for later.

## Standard's home

The human-readable security standard (what's required and why) lives in `marin-digital-standards/security/`, matching the existing pattern for accessibility, brand, and content-design — each a cross-cutting policy area with its own `README.md`, topic docs, and (where relevant) its own `scripts/`.

## Validation

Manual for v1. `marin-os/scripts/validate-security.js` and `check-security.js` are run by a developer or the `security-review` skill on demand. No GitHub Actions wiring in this phase — CI adoption is a separate future decision, not part of this plan's definition of done.

Before building any custom secret/dependency-scanning tooling: GitHub-native secret scanning, push protection, and Dependabot security updates should be turned on (confirmed off during review, except Dependabot alerts which are already on). Once enabled, `security.json`'s monitoring section records that status rather than a script re-implementing it.

**Status as of 2026-09-25: done.** A named Advanced Security configuration ("MarinOS default security") was created at the `marincountygov` org level and applied to all repositories. Confirmed via the GitHub API across all 12 org repos:

| Feature | Public repos (11) | `marin-site-template` (private) |
|---|---|---|
| Dependabot alerts | enabled | enabled |
| Dependabot security updates | enabled | not available — needs a paid GitHub Advanced Security license for this feature on a private repo |
| Secret scanning | enabled | not available — same reason |
| Secret scanning push protection | enabled | not available — same reason |

This is expected, not a gap: secret scanning and push protection are free on public repos but require a GHAS license on private ones. `marin-site-template` is a low-stakes template repo, so this is being left as-is rather than purchasing a license for it. Every deployed app in scope for this plan is public, so this doesn't affect the security work itself.

One bonus feature (`secret_scanning_validity_checks`) still reports `disabled` via the API despite being set to "Enabled" in the configuration — likely propagation lag or a naming mismatch between the configuration UI and the API field. Not one of the three core features this phase needed; worth a follow-up check later but not blocking.

## Prerequisite fixed during Phase 1

`marin-anonymizer` and `marin-unzipper` were missing `marin.yml` entirely — added, matching the existing pattern from sibling apps. `security.json` assumes every in-scope repo already has one.

While confirming this, found and fixed unrelated drift: `BRAND_VERSION` (and each `marin.yml`'s `platform.marin-ui` field) had gone stale at `1.16.2`/`1.16.3` across every app even though the actual vendored `shared/app-brand.css`/`shared/app-shell.js` content was already current at `1.17.4` — caused by files being synced by hand instead of via `marin-ui/scripts/sync-consumer.sh`, which also copies `BRAND_VERSION`. Corrected across all 8 in-scope repos so `app-maintainer`'s drift check (which compares recorded `BRAND_VERSION` against `marin-ui`'s current one) reads accurately going forward.
